1. Мета роботи

Мета роботи — набути практичних навичок модульного тестування з використанням mock-об'єктів та фреймворку Moq у мові програмування C#. Зокрема, навчитись ізолювати компоненти системи від їхніх залежностей шляхом підміни реальних об'єктів фіктивними (mock), налаштовувати поведінку mock-об'єктів за допомогою методів Setup, Returns, Throws, SetupSequence, перевіряти кількість і порядок викликів методів за допомогою Verify та MockSequence.

2. Теоретичні відомості

2.1. Mock-об'єкти та цілі їх використання

У процесі модульного тестування часто виникає необхідність ізолювати компонент, що тестується (SUT — System Under Test), від його зовнішніх залежностей: файлової системи, бази даних, мережевих служб або інших класів. Для цього застосовують тестові замінники (test doubles), найбільш потужним різновидом яких є mock-об'єкти (mocks).

Mock-об'єкт — це штучний об'єкт, що реалізує заданий інтерфейс, але замість реальної бізнес-логіки виконує заздалегідь налаштовану поведінку. Це дозволяє:

  • запускати тести без реальної інфраструктури (файлів, баз даних, мережі);
  • контролювати повернення конкретних значень або генерацію виключень;
  • перевіряти, що метод був викликаний задану кількість разів з певними аргументами;
  • перевіряти порядок взаємодії між компонентами.

2.2. Фреймворк Moq

Moq (вимовляється «Mock You» або «Mo-cue») — найпопулярніший open-source фреймворк для створення mock-об'єктів у .NET. Він базується на LINQ-виразах і лямбда-функціях, що робить код тестів лаконічним та виразним.

Основні концепції Moq:

  • Mock<T> — клас-обгортка, що генерує mock-реалізацію інтерфейсу T або абстрактного класу. Доступ до об'єкта здійснюється через властивість .Object.
  • Setup() — налаштовує очікувану поведінку для певного методу або властивості. Використовується в поєднанні з .Returns(), .Throws(), .Callback().
  • Returns() — задає значення, що повертається при виклику методу.
  • Throws() — задає виключення, яке буде кинуте при виклику методу.
  • SetupSequence() — дозволяє повертати різні значення на кожен наступний виклик одного і того ж методу.
  • Verify() — перевіряє постфактум, що метод був викликаний з певними аргументами задану кількість разів.
  • Times — клас для задання кратності перевірки: Times.Once, Times.Exactly(n), Times.Never тощо.
  • It.Is<T>(predicate) — матчер параметрів, що дозволяє налаштувати Setup для будь-якого аргументу, що задовольняє умову (предикат).
  • MockSequence — механізм перевірки порядку викликів на кількох mock-об'єктах. Потребує MockBehavior.Strict.

2.3. Впровадження залежностей (Dependency Injection) через інтерфейси

Для того, щоб компоненти системи можна було замінювати mock-об'єктами, вони мають взаємодіяти через інтерфейси, а не через конкретні класи. Цей принцип відомий як «Програмуй на рівні інтерфейсів, а не реалізацій» (Programming to an interface). Інтерфейс виступає «шов» (seam) — точкою у коді, де можна підмінити реалізацію без зміни логіки споживача.

У даній роботі бібліотека ExpressionAnalyzer побудована з трьох основних компонентів: лексичний аналізатор (ILexer), синтаксичний аналізатор (IParser) та обчислювач (IEvaluator). Додатково виділено інтерфейс джерела виразів (IExpressionSource), що дозволяє імітувати читання з файлу або іншого введення.

2.4. Фреймворк xUnit

xUnit.net — сучасний фреймворк модульного тестування для .NET, що використовує атрибут [Fact] для позначення тест-методів. Інтегрується з Visual Studio Test Explorer та підтримує конфігурацію через файл xunit.runner.json. Для перевірки очікуваних результатів використовується статичний клас Assert з методами Equal, NotNull, Throws тощо.

3.4. Тестові сценарії

У класі MockTests реалізовано п'ять тестових сценаріїв, що охоплюють основні можливості фреймворку Moq. Три mock-об'єкти створюються на рівні класу й ініціалізуються для кожного тесту заново:

private readonly Mock<IExpressionSource> _sourceMock = new();
private readonly Mock<IParser>          _parserMock  = new();
private readonly Mock<IEvaluator>       _evalMock    = new();

Сценарій 1: Нормальний пайплайн обробки виразу

Перевіряється стандартна послідовність: зчитати вираз → розібрати → обчислити. Усі три компоненти замінено mock-об'єктами. Метод Verify з Times.Once підтверджує, що кожен компонент було викликано рівно один раз.

Лістинг 7. Сценарій 1 — нормальний пайплайн

[Fact]
public void Pipeline_ValidExpression_ReturnsCorrectResult()
{
    var ast = new AstNode(NodeType.Add, new AstNode(3), new AstNode(2));
    _sourceMock.Setup(s => s.ReadExpression()).Returns("3+2");
    _parserMock.Setup(p => p.Parse("3+2")).Returns(ast);
    _evalMock.Setup(e => e.Evaluate(ast)).Returns(5.0);

    var expr   = _sourceMock.Object.ReadExpression();
    var tree   = _parserMock.Object.Parse(expr);
    var result = _evalMock.Object.Evaluate(tree);

    Assert.Equal("3+2", expr);
    Assert.Equal(NodeType.Add, tree.Type);
    Assert.Equal(5.0, result);

    _sourceMock.Verify(s => s.ReadExpression(), Times.Once);
    _parserMock.Verify(p => p.Parse("3+2"),     Times.Once);
    _evalMock.Verify(e => e.Evaluate(ast),       Times.Once);
}

Техніки Moq: Setup().Returns(), Verify(Times.Once). Тест доводить, що при коректному виразі «3+2» пайплайн повертає AST-вузол типу Add та числовий результат 5.0.

Сценарій 2: Матчер параметрів It.Is<T>

Демонструє гнучке налаштування Setup за умовою: mock парсера налаштовано відповідати на будь-який рядок, що містить символ '+'. Це дозволяє одним Setup-викликом покривати кілька різних вхідних значень.

Лістинг 8. Сценарій 2 — матчер параметрів

[Fact]
public void Parse_WithPlusInExpression_MatchedByParameterMatcher()
{
    var ast = new AstNode(NodeType.Add, new AstNode(1), new AstNode(2));
    _parserMock
        .Setup(p => p.Parse(It.Is<string>(s => s.Contains('+'))))
        .Returns(ast);

    var result1 = _parserMock.Object.Parse("1+2");
    var result2 = _parserMock.Object.Parse("10+20+30");

    Assert.NotNull(result1);
    Assert.NotNull(result2);
    Assert.Equal(NodeType.Add, result1.Type);
    Assert.Equal(NodeType.Add, result2.Type);

    _parserMock.Verify(
        p => p.Parse(It.Is<string>(s => s.Contains('+'))),
        Times.Exactly(2));
}

Техніки Moq: It.Is<string>(predicate), Verify(Times.Exactly(n)). Verify підтверджує, що метод Parse з рядком, що містить '+', викликано рівно двічі.

Сценарій 3: Генерація виключення mock-об'єктом

Перевіряється поведінка системи у разі збою джерела даних. Mock-об'єкт IExpressionSource налаштовано кидати FileNotFoundException із заданим іменем файлу. Тест перевіряє, що виключення правильно поширюється і містить очікувані дані.

Лістинг 9. Сценарій 3 — виключення

[Fact]
public void ReadExpression_SourceThrowsFileNotFoundException_ExceptionPropagated()
{
    _sourceMock
        .Setup(s => s.ReadExpression())
        .Throws(new FileNotFoundException("File not found", "expr.txt"));

    var ex = Assert.Throws<FileNotFoundException>(
        () => _sourceMock.Object.ReadExpression());

    Assert.Equal("expr.txt", ex.FileName);
    Assert.Contains("File not found", ex.Message);

    _sourceMock.Verify(s => s.ReadExpression(), Times.Once);
}

Техніки Moq: Setup().Throws(). Assert.Throws<T> (xUnit) перехоплює виключення і повертає його для подальшої перевірки властивостей FileName та Message.

Сценарій 4: Різні відповіді на послідовні виклики (SetupSequence)

Демонструє SetupSequence — механізм Moq для налаштування різних відповідей на кожен наступний виклик одного методу. Обчислювач послідовно повертає 11.0, 0.0 і −5.0.

Лістинг 10. Сценарій 4 — SetupSequence

[Fact]
public void Evaluate_CalledThreeTimes_ReturnsDifferentResultEachCall()
{
    var ast = new AstNode(42.0);
    _evalMock
        .SetupSequence(e => e.Evaluate(ast))
        .Returns(11.0)
        .Returns(0.0)
        .Returns(-5.0);

    var r1 = _evalMock.Object.Evaluate(ast);
    var r2 = _evalMock.Object.Evaluate(ast);
    var r3 = _evalMock.Object.Evaluate(ast);

    Assert.Equal(11.0, r1);
    Assert.Equal(0.0,  r2);
    Assert.Equal(-5.0, r3);

    _evalMock.Verify(e => e.Evaluate(ast), Times.Exactly(3));
}

Техніки Moq: SetupSequence().Returns().Returns().Returns(). Цей сценарій моделює, наприклад, поведінку генератора або зчитувача потоку значень.

Сценарій 5: Перевірка порядку та кількості викликів (MockSequence)

Перевіряє, що компоненти пайплайну викликаються у визначеному порядку: спочатку ReadExpression, потім Parse, потім Evaluate. Використовується MockSequence — механізм суворого контролю порядку. Для цього mock-об'єкти створюються з MockBehavior.Strict, що забороняє будь-які виклики, не передбачені у Setup.

Лістинг 11. Сценарій 5 — MockSequence

[Fact]
public void Pipeline_VerifyCallOrderAndExactCount()
{
    var strictSource = new Mock<IExpressionSource>(MockBehavior.Strict);
    var strictParser = new Mock<IParser>(MockBehavior.Strict);
    var strictEval   = new Mock<IEvaluator>(MockBehavior.Strict);

    var ast      = new AstNode(NodeType.Multiply, new AstNode(3), new AstNode(4));
    var sequence = new MockSequence();

    strictSource.InSequence(sequence).Setup(s => s.ReadExpression()).Returns("3*4");
    strictParser.InSequence(sequence).Setup(p => p.Parse("3*4")).Returns(ast);
    strictEval.InSequence(sequence).Setup(e => e.Evaluate(ast)).Returns(12.0);

    var expr   = strictSource.Object.ReadExpression();
    var tree   = strictParser.Object.Parse(expr);
    var result = strictEval.Object.Evaluate(tree);

    Assert.Equal("3*4",         expr);
    Assert.Equal(NodeType.Multiply, tree.Type);
    Assert.Equal(12.0,          result);

    strictSource.Verify(s => s.ReadExpression(), Times.Once);
    strictParser.Verify(p => p.Parse("3*4"),     Times.Once);
    strictEval.Verify(e => e.Evaluate(ast),       Times.Once);
}

Техніки Moq: MockBehavior.Strict, MockSequence, InSequence(sequence).Setup(). Якщо виклики відбудуться не в заданому порядку, MockBehavior.Strict кине виключення, що зробить тест неуспішним.

5. Висновок

У ході виконання програмного проєкту 2 було розроблено п'ять модульних тестів з використанням фреймворку Moq та xUnit для тестування компонентів бібліотеки ExpressionAnalyzer.

Було реалізовано та перевірено наступні можливості Moq:

  • базову підміну залежностей з налаштуванням Setup().Returns() та перевіркою Verify(Times.Once);
  • гнучке налаштування поведінки за умовою за допомогою матчера It.Is<T>(predicate);
  • імітацію збою залежності (генерація виключень) через Setup().Throws();
  • налаштування різних відповідей на послідовні виклики за допомогою SetupSequence;
  • суворий контроль порядку взаємодії між компонентами через MockSequence та MockBehavior.Strict.

Використання mock-об'єктів забезпечило повну ізоляцію кожного компонента системи: тести не звертаються до файлової системи, не залежать від реальних реалізацій лексера, парсера чи обчислювача. Це дозволяє виявляти дефекти на рівні контракту (інтерфейсу), а не реалізації.

Принцип впровадження залежностей через інтерфейси (ILexer, IParser, IEvaluator, IExpressionSource) виявився ключовим для можливості ефективного використання mock-об'єктів. Чітке розмежування компонентів через інтерфейси дозволяє тестувати кожен компонент незалежно та забезпечує відповідність принципу єдиної відповідальності (SRP).

Результат: всі 5 тестів успішно пройдено, кодова база залишається стабільною та готовою до подальшого розвитку.
