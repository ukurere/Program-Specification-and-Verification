1. Мета роботи

Мета роботи — набути практичних навичок статичного аналізу коду за допомогою Roslyn-аналізатора SonarAnalyzer.CSharp та збору метрик якості коду за допомогою Microsoft.CodeAnalysis.Metrics. Зокрема, навчитись виявляти потенційні дефекти та проблеми підтримуваності без запуску програми, інтерпретувати метрики Cyclomatic Complexity та Maintainability Index, а також проводити цілеспрямований рефакторинг для покращення якості коду.

2. Теоретичні відомості

2.1. Статичний аналіз коду

Статичний аналіз коду (static code analysis) — це автоматизована перевірка вихідного коду без його виконання. Аналізатор досліджує синтаксичне дерево (AST) та семантичну модель програми, виявляє порушення правил кодування, потенційні помилки та проблеми якості.

Переваги статичного аналізу:

  • виявлення дефектів на ранньому етапі — до компіляції або запуску тестів;
  • виявлення класу помилок, які важко відтворити у тестах (переповнення, некоректні порівняння float);
  • об'єктивна оцінка якості і складності коду через метрики;
  • інтеграція у CI/CD — автоматична перевірка при кожному коміті.

2.2. Roslyn та SonarAnalyzer.CSharp

Roslyn (Microsoft .NET Compiler Platform) — платформа компіляторів C# та VB.NET з відкритим API для аналізу коду. Roslyn дозволяє стороннім бібліотекам підключатись як аналізатори (Roslyn Analyzers) і отримувати діагностичні повідомлення під час компіляції.

SonarAnalyzer.CSharp — набір Roslyn-аналізаторів від компанії SonarSource (розробники SonarQube). Підключається до проєкту як NuGet-пакет і перевіряє код на понад 500 правил якості, надійності та безпеки без потреби у зовнішньому сервері SonarQube.

2.3. Правило S1244: порівняння чисел з плаваючою комою

Назва: Floating point numbers should not be tested for equality
Категорія: Bug / Reliability    Серйозність: Major

Числа з плаваючою комою (тип double та float) зберігаються у форматі IEEE 754 та можуть мати похибку округлення. Результат арифметичної операції може незначно відрізнятися від очікуваного математичного результату, що призводить до хибного результату при точному порівнянні:

// Небезпечно — може дати хибний результат через похибку округлення
if (divisor == 0)
    throw new DivideByZeroException();

// Безпечно — порівняння з допуском epsilon
if (Math.Abs(divisor) < 1e-10)
    throw new DivideByZeroException();

Значення epsilon (1e-10) обирається відповідно до необхідної точності обчислень.

2.4. Метрики якості коду

Microsoft.CodeAnalysis.Metrics — офіційна бібліотека Microsoft для збору метрик якості коду. Запускається як MSBuild-ціль: dotnet build ExpressionAnalyzer.csproj -t:Metrics. Результат записується у XML-файл.

Основні метрики:

МетрикаОписНорма
Cyclomatic Complexity (CC) Кількість лінійно незалежних шляхів виконання у методі. Кожна розгалуження (if, while, case, &&, ||) збільшує CC на 1. ≤ 10 на метод
Maintainability Index (MI) Індекс підтримуваності (0–100), розрахований на основі CC, числа рядків та індексу Halstead. Вищий — краще. ≥ 65
Class Coupling Кількість унікальних типів, від яких залежить клас/метод. ≤ 9
Depth of Inheritance Глибина дерева успадкування класу. ≤ 5
Lines of Source (LoS) Кількість рядків вихідного коду (без порожніх і коментарів). —

2.5. Cyclomatic Complexity та тестуваність

Cyclomatic Complexity (CC) безпосередньо пов'язана з кількістю тест-кейсів, необхідних для 100% покриття гілок: метод з CC = N вимагає щонайменше N тестів. Метод з CC > 10 вважається складним і схильним до помилок. Рефакторинг такого методу (декомпозиція на приватні методи) знижує CC кожного з підметодів, навіть якщо сумарний CC assembly зростає.

2.6. Maintainability Index та формула розрахунку

MI розраховується за формулою Коулмана–Брауна на основі трьох параметрів: метрик Halstead (обсяг коду), CC та кількості рядків. MI у діапазоні 0–64 означає низьку підтримуваність (код важкий для розуміння та змін). MI ≥ 65 вважається прийнятним, MI ≥ 85 — відмінним.

3.4. Рефакторинг: виправлення S1244

Точне порівняння divisor == 0 замінено на epsilon-порівняння через функцію Math.Abs. Значення epsilon 1e-10 обрано як достатньо малий допуск для задач арифметики з подвійною точністю.

Лістинг 3. Evaluator.cs — до і після виправлення

// ДО: точне порівняння (S1244)
case NodeType.Divide:
    double divisor = Evaluate(node.Right!);
    if (divisor == 0)
        throw new DivideByZeroException("Division by zero");
    return Evaluate(node.Left!) / divisor;

// ПІСЛЯ: epsilon-порівняння (S1244 усунуто)
case NodeType.Divide:
    double divisor = Evaluate(node.Right!);
    if (Math.Abs(divisor) < 1e-10)
        throw new DivideByZeroException("Division by zero");
    return Evaluate(node.Left!) / divisor;

Після цієї зміни повторна компіляція dotnet build не виводить жодних Sonar-попереджень.

3.5. Рефакторинг: покращення Lexer (MI 54 → 70)

Метод Lexer.Tokenize мав MI = 54 через монолітну структуру: один великий метод з вкладеним циклом, умовами і switch-виразом. Відповідно до принципу єдиної відповідальності (SRP), метод розбито на три приватні допоміжні методи.

Лістинг 4. Lexer.cs — до рефакторингу (монолітний метод)

public IReadOnlyList<Token> Tokenize(string expression)
{
    var tokens = new List<Token>();
    int i = 0;
    while (i < expression.Length)
    {
        char c = expression[i];
        if (char.IsWhiteSpace(c)) { i++; continue; }
        if (char.IsDigit(c) || c == '.')
        {
            int start = i;
            while (i < expression.Length
                   && (char.IsDigit(expression[i]) || expression[i] == '.'))
                i++;
            double val = double.Parse(
                expression[start..i], CultureInfo.InvariantCulture);
            tokens.Add(new Token(TokenType.Number, val));
            continue;
        }
        var type = c switch
        {
            '+' => TokenType.Plus,
            '-' => TokenType.Minus,
            '*' => TokenType.Star,
            '/' => TokenType.Slash,
            '(' => TokenType.LParen,
            ')' => TokenType.RParen,
            _   => throw new InvalidOperationException($"Unknown character '{c}'")
        };
        tokens.Add(new Token(type));
        i++;
    }
    tokens.Add(new Token(TokenType.End));
    return tokens;
}

Лістинг 5. Lexer.cs — після рефакторингу (декомпозиція на 3 методи)

public IReadOnlyList<Token> Tokenize(string expression)
{
    var tokens = new List<Token>();
    int i = 0;
    while (i < expression.Length)
    {
        char c = expression[i];
        if (char.IsWhiteSpace(c)) { i++; continue; }
        if (IsNumberStart(c)) { tokens.Add(ReadNumber(expression, ref i)); continue; }
        tokens.Add(new Token(MapCharToTokenType(c)));
        i++;
    }
    tokens.Add(new Token(TokenType.End));
    return tokens;
}

private static bool IsNumberStart(char c) => char.IsDigit(c) || c == '.';

private static Token ReadNumber(string expression, ref int i)
{
    int start = i;
    while (i < expression.Length && IsNumberStart(expression[i]))
        i++;
    double val = double.Parse(expression[start..i], CultureInfo.InvariantCulture);
    return new Token(TokenType.Number, val);
}

private static TokenType MapCharToTokenType(char c) => c switch
{
    '+' => TokenType.Plus,
    '-' => TokenType.Minus,
    '*' => TokenType.Star,
    '/' => TokenType.Slash,
    '(' => TokenType.LParen,
    ')' => TokenType.RParen,
    _   => throw new InvalidOperationException($"Unknown character '{c}'")
};

Виділено три приватні методи:

  • IsNumberStart(char) — предикат початку числового токена;
  • ReadNumber(string, ref int) — зчитує і повертає числовий токен, просуваючи позицію i;
  • MapCharToTokenType(char) — відображає символ оператора на тип токена.

Кожен метод виконує одну задачу — відповідно до принципу SRP. Головний метод Tokenize скоротився з 28 рядків до 10 і тепер описує лише загальну логіку циклу.

5. Висновок

У ході виконання програмного проєкту 4 проведено статичний аналіз коду бібліотеки ExpressionAnalyzer з використанням Roslyn-аналізатора SonarAnalyzer.CSharp 10.26 та зібрано метрики якості засобами Microsoft.CodeAnalysis.Metrics.

Аналізатор виявив одне порушення правила S1244 — точне порівняння значення типу double на рівність нулю у методі Evaluator.Evaluate. Це потенційний дефект надійності, що може призвести до пропуску ділення на нуль через похибку округлення IEEE 754. Порушення виправлено заміною divisor == 0 на epsilon-порівняння Math.Abs(divisor) < 1e-10.

Метрики виявили низьке значення Maintainability Index (MI = 54) для методу Lexer.Tokenize (норма ≥65), зумовлене монолітною структурою методу. Проведено рефакторинг: метод декомпозовано на три приватні допоміжні методи (IsNumberStart, ReadNumber, MapCharToTokenType), кожен з яких відповідає за одну задачу. Після рефакторингу MI класу Lexer зріс до 70, що відповідає нормі.

Статичний аналіз довів свою ефективність як засіб раннього виявлення дефектів: S1244 не був би знайдений звичайними тестами, оскільки в тестовому середовищі дільник може бути точно рівним нулю. У реальному застосуванні, де дільник є результатом складних обчислень, похибка округлення може призвести до непомічення ділення на нуль.
