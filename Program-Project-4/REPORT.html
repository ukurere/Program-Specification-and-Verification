1. Мета роботи

Мета роботи — набути практичних навичок статичного аналізу коду за допомогою Roslyn-аналізатора SonarAnalyzer.CSharp та збору метрик якості коду за допомогою бібліотеки Microsoft.CodeAnalysis.Metrics. Зокрема: навчитись виявляти потенційні дефекти у коді без його виконання, інтерпретувати метрики Cyclomatic Complexity та Maintainability Index, а також проводити цілеспрямований рефакторинг для покращення якості та підтримуваності коду.

2. Теоретичні відомості

2.1. Статичний аналіз коду

Статичний аналіз коду (static code analysis) — це автоматизована перевірка вихідного коду без його виконання. Аналізатор досліджує синтаксичне дерево (AST) та семантичну модель програми і виявляє потенційні дефекти, порушення правил кодування та проблеми підтримуваності.

На відміну від динамічного аналізу (тестування), статичний аналіз виявляє цілий клас проблем, які важко або неможливо відтворити у тестах: неточні порівняння чисел з плаваючою комою, потенційні витоки ресурсів, недосяжний код, некоректне перетворення типів. Крім того, аналіз виконується для всього коду одразу — не тільки для шляхів, покритих тестами.

2.2. Платформа Roslyn та SonarAnalyzer.CSharp

Roslyn (Microsoft .NET Compiler Platform) — відкрита платформа компіляторів C# від Microsoft, яка надає API для програмного аналізу коду. Сторонні розробники можуть створювати Roslyn-аналізатори — бібліотеки, що підключаються до процесу компіляції та отримують повну семантичну модель кожного файлу.

SonarAnalyzer.CSharp (версія 10.26.0) — набір Roslyn-аналізаторів від компанії SonarSource. Підключається як NuGet-пакет; активується автоматично при кожному виклику dotnet build. Перевіряє код на понад 500 правил якості, надійності та безпеки без потреби у зовнішньому сервері SonarQube.

2.3. Правило S1244 — порівняння чисел з плаваючою комою

Назва: Floating point numbers should not be tested for equality
Категорія: Bug / Reliability     Серйозність: Major

Числа типу double та float зберігаються у форматі IEEE 754 і накопичують похибку округлення при арифметичних операціях. Навіть математично точний нуль може зберігатися як -2.77e-17 після ланцюжка обчислень. Точне порівняння divisor == 0 в такому разі поверне false — і ділення на «майже нуль» відбудеться без виключення.

Безпечна альтернатива — порівняння з допуском (epsilon):

// Небезпечно — S1244
if (divisor == 0) ...

// Безпечно — epsilon-порівняння
if (Math.Abs(divisor) < 1e-10) ...

Microsoft.CodeAnalysis.Metrics — офіційна MSBuild-ціль для збору метрик якості. Запускається командою:

dotnet build ExpressionAnalyzer.csproj -t:Metrics

3.5. Рефакторинг Evaluator — виправлення S1244

Точне порівняння divisor == 0 замінено на epsilon-порівняння через функцію Math.Abs. Значення допуску 1e-10 обрано як достатньо мале для задач арифметики з подвійною точністю (тип double має ~15–16 значущих цифр).

Лістинг 3. Evaluator.cs — до і після виправлення S1244

// ДО: точне порівняння — S1244
case NodeType.Divide:
    double divisor = Evaluate(node.Right!);
    if (divisor == 0)
        throw new DivideByZeroException("Division by zero");
    return Evaluate(node.Left!) / divisor;

// ПІСЛЯ: epsilon-порівняння — S1244 усунуто
case NodeType.Divide:
    double divisor = Evaluate(node.Right!);
    if (Math.Abs(divisor) < 1e-10)
        throw new DivideByZeroException("Division by zero");
    return Evaluate(node.Left!) / divisor;

Після цієї зміни повторна компіляція не виводить жодних Sonar-попереджень. MI методу залишився незмінним — 81, CC = 9 (обидва в нормі).

3.6. Рефакторинг Lexer — підвищення MI з 54 до 70

Причина низького MI у Lexer — монолітний метод Tokenize: один метод із 38 рядків містив вкладений цикл, дві умовні гілки та switch-вираз. Відповідно до принципу єдиної відповідальності (SRP), метод декомпозовано на три приватні допоміжні методи.

Лістинг 4. Lexer.cs — до рефакторингу (монолітний метод)

public IReadOnlyList<Token> Tokenize(string expression)
{
    var tokens = new List<Token>();
    int i = 0;
    while (i < expression.Length)
    {
        char c = expression[i];
        if (char.IsWhiteSpace(c)) { i++; continue; }
        if (char.IsDigit(c) || c == '.')      // логіка числа вбудована прямо тут
        {
            int start = i;
            while (i < expression.Length
                   && (char.IsDigit(expression[i]) || expression[i] == '.'))
                i++;
            double val = double.Parse(
                expression[start..i], CultureInfo.InvariantCulture);
            tokens.Add(new Token(TokenType.Number, val));
            continue;
        }
        var type = c switch   // і маппінг операторів тут же
        {
            '+' => TokenType.Plus,
            '-' => TokenType.Minus,
            '*' => TokenType.Star,
            '/' => TokenType.Slash,
            '(' => TokenType.LParen,
            ')' => TokenType.RParen,
            _   => throw new InvalidOperationException($"Unknown character '{c}'")
        };
        tokens.Add(new Token(type));
        i++;
    }
    tokens.Add(new Token(TokenType.End));
    return tokens;
}

Лістинг 5. Lexer.cs — після рефакторингу (декомпозиція)

// Головний метод — тільки загальний цикл, деталі винесені
public IReadOnlyList<Token> Tokenize(string expression)
{
    var tokens = new List<Token>();
    int i = 0;
    while (i < expression.Length)
    {
        char c = expression[i];
        if (char.IsWhiteSpace(c)) { i++; continue; }
        if (IsNumberStart(c)) { tokens.Add(ReadNumber(expression, ref i)); continue; }
        tokens.Add(new Token(MapCharToTokenType(c)));
        i++;
    }
    tokens.Add(new Token(TokenType.End));
    return tokens;
}

// Предикат: чи починається число з цього символу?
private static bool IsNumberStart(char c) => char.IsDigit(c) || c == '.';

// Зчитування числового токена з просуванням позиції
private static Token ReadNumber(string expression, ref int i)
{
    int start = i;
    while (i < expression.Length && IsNumberStart(expression[i]))
        i++;
    double val = double.Parse(expression[start..i], CultureInfo.InvariantCulture);
    return new Token(TokenType.Number, val);
}

// Відображення символу оператора на тип токена
private static TokenType MapCharToTokenType(char c) => c switch
{
    '+' => TokenType.Plus,
    '-' => TokenType.Minus,
    '*' => TokenType.Star,
    '/' => TokenType.Slash,
    '(' => TokenType.LParen,
    ')' => TokenType.RParen,
    _   => throw new InvalidOperationException($"Unknown character '{c}'")
};

Виділено три приватних методи, кожен з яких виконує рівно одну задачу:

  • IsNumberStart(char) — предикат початку числового токена (MI = 92, CC = 2);
  • ReadNumber(string, ref int) — зчитує числовий токен, просуває позицію (MI = 74, CC = 3);
  • MapCharToTokenType(char) — відображає символ оператора на тип токена (MI = 87, CC = 1).

Головний метод Tokenize скоротився з 28 до 10 рядків і тепер описує виключно загальний алгоритм обходу символів.

5. Висновок

У ході виконання програмного проєкту 4 проведено статичний аналіз коду бібліотеки ExpressionAnalyzer з використанням Roslyn-аналізатора SonarAnalyzer.CSharp 10.26.0 та зібрано метрики якості засобами Microsoft.CodeAnalysis.Metrics 4.14.0.

Аналізатор виявив порушення правила S1244 — точне порівняння значення типу double у методі Evaluator.Evaluate. Це потенційний дефект надійності категорії Major: через похибку округлення IEEE 754 перевірка divisor == 0 може не спрацювати для «майже нульового» дільника. Виправлення полягало у заміні на epsilon-порівняння Math.Abs(divisor) < 1e-10.

Збір метрик виявив низький Maintainability Index класу Lexer — MI = 54 (норма ≥ 65). Причина — монолітний метод Tokenize з вкладеними структурами управління. Рефакторинг у відповідності до принципу єдиної відповідальності (SRP) — декомпозиція на методи IsNumberStart, ReadNumber та MapCharToTokenType — підняв MI класу до 70. Додатково, CC методу Tokenize знизився з 8 до 4, що поліпшує його тестуваність.

Після рефакторингу всі 5 тестів залишились успішними — коректність бібліотеки підтверджена. Статичний аналіз довів свою ефективність як засіб виявлення прихованих дефектів та проблем якості, що не виявляються звичайним тестуванням.
